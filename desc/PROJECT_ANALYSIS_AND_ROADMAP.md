# TimeCollate (拾光集) 项目现状分析与未来发展路线图

## 1. 项目当前技术与业务状态评估

目前，`TimeCollate (拾光集)` 已经从一个纯前端的 LocalStorage 草稿应用，演进为一套具备**生产级后端架构**支撑的 Web 记忆留存（时光书）平台。

### 1.1 技术栈与架构现状

*   **前端工程 (`time-collate`)**：
    *   **核心框架**：React 19 + TypeScript + Vite + Zustand (状态管理) + Tailwind CSS v4。
    *   **核心能力**：基于 `@dnd-kit` 的章节拖拽排序，基于 `react-pageflip` 的 3D 物理翻书动效，多布局（`Magazine`、`Collage`、`Journal` 等）动态渲染器。
    *   **鉴权与路由**：集成了全局 Axios 拦截器，使用 React Router v7 实现了 `AuthGuard`（用户路由守卫）与 `AdminGuard`（管理员路由守卫）。
*   **后端服务 (`server`)**：
    *   **基础选型**：Express + MySQL 8.0 (带连接池) + ES Modules + TypeScript。
    *   **存储防腐层**：设计了清晰的 `IStorageService` 接口，使用**工厂模式**根据环境变量切换 `R2StorageService` 或 `AliyunOssStorageService`。支持图片上传、私有读写、临时签名（Presigned URLs）和缩略图映射。
    *   **管理后台系统**：包含了完整管理面板 API，可对用户（禁用/激活）、书籍（审核发布）、反馈（Pending/Processed）进行全面管理。
    *   **导出策略模式**：设计了 `IExportStrategy` 接口，目前有 `Markdown`、`OfflineHtml` 和 `Pdf` (基于 Playwright 无头浏览器渲染) 三种导出实现。

## 2. 核心架构缺陷与瓶颈分析 (防御性设计评估)

在 10x 并发量或 10x 数据量级下，现有系统存在以下脆弱环节：

### 2.1 导出引擎 CPU 挂起与内存溢出 (OOM) 隐患
*   **现状**：`/api/export/pdf` 直接在主进程中同步拉起无头浏览器实例。
*   **风险**：Playwright 浏览器实例是极度消耗 CPU 和内存的。在 2C2G 服务器上，2 个以上的并发 PDF 导出请求就可能触发 OOM 导致后端崩溃。
*   **解决思路**：必须改造为**异步任务队列（BullMQ + Redis）**，限制并发处理数，实现削峰填谷。

### 2.2 拼贴布局中图片宽高元数据缺失
*   **现状**：`photos` 表设计了 `width` 和 `height` 字段，但在图片上传时（`upload.ts`）和前端保存时，并未抓取和填充此数据。
*   **影响**：前端的 `CollageLayout` (拼贴布局) 只能盲目按照固定比例（如 1:1 或 4:3）填充，无法真正实现“根据图片原始比例自适应排版的杂志级视觉”。
*   **解决思路**：在后端上传拦截器中利用 `sharp` 库自动抓取图片 `metadata`（宽高、旋转方向），并在数据库中落库。

### 2.3 零信任权限校验的完整性
*   **现状**：引入了用户体系，但是在各别复杂的业务链条中（例如批量删除章节、修改分享状态），依然存在直接依赖前端传入主键 `id` 且未严格与当前会话 `user_id` 作联合校验的隐患。
*   **解决思路**：需要全面推行安全规范：**所有修改与物理删除，必须强制绑定 JWT 解析出的 `req.user.id` 作为条件**。

## 3. 建议继续拓展的核心功能

为了提升项目的市场竞争力、用户粘性和技术壁垒，建议逐步引入以下特性：

### 3.1 智能化与动态化排版 (AI Layout)
*   **智能拼贴引擎**：根据页面图片数量和宽高比（从数据库中读取的高宽比），利用算法从 `LayoutRegistry` 中选择最佳适配的杂志/相册版式，免去用户手动调整的繁琐。
*   **在线文字溢出检测**：印刷版时光书最容易遇到文字超出页面容器的问题。当用户输入超过 A4 物理边框时，实时气泡提醒，或自动申请“新增续页”。
*   **排版主题商店**：提供更多视觉气质的主题（如“日系清新”、“黑白纪实”、“经典家庭相册”），支持更丰富的字体（如 Google 免费商用中文字体库）动态载入。

### 3.2 离线化与跨端生态 (WeChat Mini-Program & Mobile)
*   **微信小程序端**：考虑到时光书的主要分享与传播场景是朋友圈和微信群，`users` 表已预留了 `openid`。开发微信小程序版本作为快速记录、上传照片的入口，而 Web 端则作为大屏精修和导出终端。
*   **H5 翻书分享页优化**：移动端适配当前的 `SharedBookViewer.tsx`，将大屏翻书优化为更符合移动端单手上下滑动或横向模拟翻页的交互。

### 3.3 协作式时光书 (Co-authoring Book)
*   **多人共创模式**：支持一本书绑定多个 `user_id`（主创 + 协作者），非常适合家庭（夫妻共创宝宝时光书）、班级（毕业纪念册）、旅行同伴共同记录。
*   **章节锁定与版本树**：当 A 用户在编辑第 1 章时，锁定该章节，防止 B 用户覆盖写入。

## 4. 后续开发计划与实施路径

### 4.1 阶段二：高可用异步导出与图像元数据落库（当前重点推进）
1.  **后端引入 Redis + BullMQ 框架**：
    *   在 Express 后端引入 `bullmq`。
    *   限制并发 Worker 数为 `1` (或根据 CPU 核数动态调整)，确保 2C2G 服务器稳定。
    *   将 PDF/HTML 导出改为异步任务。
2.  **前端适配异步导出 UI**：
    *   设计 `ExportProgressModal`，点击导出后，向后端轮询任务状态（Queueing、Processing、Completed）。
    *   任务完成时提供云端 Presigned 下载 URL，支持断点续传。
3.  **抓取图片真实尺寸**：
    *   后端 `upload.ts` 引入 `sharp`（或利用前端 Canvas 获取），落库时必须存储图片的 `width` 和 `height`。

### 4.2 阶段三：智能排版引擎与零信任安全隔离加固
1.  **杂志级自适应拼贴**：
    *   优化 `GridLayout` 与 `CollageLayout`，使其获取到照片宽高比后，能自适应计算排版格数（如：横图占双栏，竖图占单栏）。
2.  **安全加固 (零信任规范)**：
    *   严格排查所有 `DELETE` / `UPDATE` 路由，杜绝水平越权漏洞。
    *   对大厅分享链接启用失效时间限制（Expires At）。

### 4.3 阶段四：微信小程序生态与多人协作时光书
1.  **微信快捷登录**：
    *   开发微信 OAuth 服务端。绑定已有用户的 `openid`，支持多端数据同步。
2.  **多人协作模型**：
    *   数据库表升级：新增 `book_collaborators`（书籍协作者关联表）。
    *   引入章节级别的分布式乐观锁，避免冲突。
